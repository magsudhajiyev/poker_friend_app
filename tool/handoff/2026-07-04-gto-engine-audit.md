# Handoff: audit `poker_friend_engine`'s GTO ranges for the drill trainer

**From:** session working on branch `claude/gto-baseline` of `poker_friend_app`
**Date:** 2026-07-04

## Context (read this first)

The app has a premium Training Drills feature (preflop spot trainer vs bots
modelled on the user's saved opponents). Every hero decision is graded two
ways — a **GTO baseline** and an **exploit line** — by:

- `lib/services/drill_gto_charts.dart` — curated ~100BB position-pair charts
  (RFI, defend-vs-open keyed by both positions, vs-3-bet by opener seat),
  a chart-derived playability ordering used for exploit widening/tightening,
  and a new MTT/ante mode (`anteWidenPct`, `sbCompleteCutoff`).
- `lib/services/drill_nash_pushfold.dart` — self-computed Nash push/fold for
  ≤20BB (generated by `tool/nash/`, provenance in `tool/nash/README.md`).
- `lib/services/drill_grader.dart` — membership checks + verdict math; every
  grade carries a `trace` (logged via debugPrint) showing exactly which chart
  produced the decision.
- Tests: `test/services/drill_gto_baseline_test.dart` (20 scenarios).

Recent fix that motivates this audit: the SB first-in spot was modelled
raise-or-fold (cash convention); in MTT/ante formats the solver SB is
complete-or-raise and folds only ~10% of hands. We added a Format toggle
(Cash / MTT·Ante) and an SB completion strategy (continue = top 75% of
playability), but the numbers are curated approximations.

**The user has explicitly authorized using real chart data** to calibrate or
replace these ranges.

## The task

Audit the `gto_engine` module in `magsudhajiyev/poker_friend_engine`
(FastAPI backend, deployed at poker-friend-engine.onrender.com, consumed by
the app via `/api/v1/analyze-hand` with an `X-API-Key` header) and answer:

1. **What range data does it hold?** Positions covered, stack depths, cash
   vs MTT/ante variants, and the encoding (binary sets vs per-hand action
   frequencies on the 169 grid).
2. **Should the app's drills source ranges from it?** Options to weigh:
   (a) a build-time export of the backend's ranges into the Dart chart files
   (keeps drills offline-capable — they currently work with zero network),
   (b) a new backend endpoint the app fetches + caches, or
   (c) keep the curated Dart charts but calibrate their numbers against the
   engine's data. Offline capability and the existing trace/debuggability
   should be preserved whichever way.
3. **Mixed strategies:** if the engine stores per-hand frequencies, the
   grader could grade against actual mixes (e.g. "65o SB ante: complete 88% /
   raise 12%") instead of the current close-band approximation
   (`_closeBand = 4.0` playability points, `mixedRaiseOk` for SB completes).

## Specific calibration questions for the engine data

- SB first-in with ante: what fraction of hands pure-fold? (Reference grid
  the user provided suggested ~10%; the app currently folds 25% —
  `sbCompleteCutoff = 75.0` in `drill_gto_charts.dart`.)
- Ante widening: the app applies a flat +3% (`anteWidenPct`) to all RFI
  ranges. What does the engine's data imply per position?
- Stack-depth profiles: the app maps >60BB→100bb charts, 20–60BB→40bb
  (calls tightened 35%), ≤20BB→Nash. Does the engine have real 40BB/60BB
  ranges to replace the interpolation?
